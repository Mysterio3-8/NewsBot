# AI News Rewriter

**Статус:** 🟢 прод (первая реальная публикация состоялась 2026-07-02 — 12 постов вживую в TG-канал `@NewsThreeWord` и VK-группу `233689032`. LLM по умолчанию — облачный **Groq** (`llama-3.1-8b-instant`). Ollama пробовали дефолтом 2026-07-03, но на этой машине (8 ГБ RAM, без GPU) она непригодно медленная (>60с/вызов на CPU) — пользователь решил вернуться на Groq до появления сервера с GPU (см. Инварианты). Groq остаётся дефолтом, Ollama — резерв в коде. См. Checkpoint)

## Что это

Десктопное приложение (Python + PySide6), которое отслеживает заданные Telegram-каналы и VK-сообщества, отбирает новостные посты, переписывает их через LLM (по умолчанию облачный Groq, опционально локальная Ollama или Gemini), готовит изображения с watermark и публикует по расписанию в Telegram и VK.

Полная спецификация: [SPEC.md](SPEC.md) — читать перед первой задачей в новой сессии.

**Открытая задача на след. сессию: [NEXT_SESSION.md](NEXT_SESSION.md)** — незавершённый перевод VPS на git-деплой (упёрлись в защиту на `rm -rf`/чекаут, нужно разрешение пользователя или он делает вручную); три новые фичи по фото (обрезка вотермарка вместо подмены, заголовок только на первом фото, ужесточённый промпт детекции) не проверены на реальном живом посте, только юнит-тестами; ждём от пользователя примеры вотермарков и образцовые посты для калибровки рерайта. Читать перед началом работы, удалять пункты по мере выполнения.

## Архитектура (кратко)

```
Источники (TG/VK) → Фильтрация → LLM классификация → LLM rewrite
    → Изображения (пост/сток-API/локальная генерация) → Watermark
    → Очередь публикации → Telegram/VK
```

Подробности: разделы 4, 8–14 в [SPEC.md](SPEC.md).

## Toolchain / зависимости

- Python 3.12+ (см. грабли — локальный venv на 3.10.11)
- LLM: по умолчанию облачный **Groq API** (`llm.provider: "groq"`, модель `llama-3.1-8b-instant`, бесплатный tier — 14 400 запросов/день + 500k токенов/день, работает из РФ без VPN, LPU-чипы ~2000 токенов/сек, нужен `GROQ_API_KEY` в `.env` — см. https://console.groq.com/keys). Запасные: локальная **Ollama** (`llm.provider: "ollama"`, `qwen2.5:3b`, `llm.host: "http://localhost:11434"` — вернётся дефолтом на сервере с GPU; на текущем ноуте без GPU >60с/вызов, непригодно) и **Gemini** (`llm.provider: "gemini"`, геоблок для РФ + лимит 20 запросов/день — не рекомендуется).
- Telethon (MTProto, чтение чужих TG-каналов) + aiogram (публикация в TG)
- vk_api (чтение и публикация VK), APScheduler, Pillow, SQLAlchemy, PySide6, pytest/pytest-asyncio
- Опционально: локальный сервер Stable Diffusion (AUTOMATIC1111-совместимый API) для `LocalAIImageProvider`
- Секреты — только в `.env` (см. `.env.example`), никогда в `config.yaml` или коде

### Веб-лаунчер (одна кнопка) — 2026-07-03

`start.bat` в корне проекта — двойной клик активирует venv, запускает `app/web_launcher.py`
(Flask, localhost:5000) и открывает браузер автоматически. На странице — кнопка
"Старт"/"Стоп" (оборачивает `headless_service.run_forever` в фоновом потоке со своим
asyncio-циклом) и таблица последних публикаций **в московском времени** (не UTC — раньше
таких часов на странице не было, только `published_at` в БД в UTC, что было бы путающим
при первом взгляде на страницу). Остановка — через `stop_event`, потокобезопасно
переданный туда через `loop.call_soon_threadsafe`.

**Важно:** без явного `next_run_time` при `scheduler.add_job()` первый цикл проверки
ждал бы полный `check_interval_minutes` (по умолчанию 4 часа) прежде чем сделать
хоть что-то — кнопка "Старт" выглядела бы так, будто ничего не происходит.
Исправлено в `headless_service.py::run_forever` — первый цикл теперь стартует сразу
после нажатия "Старт", дальше идёт по обычному расписанию. Антиспам-стопор
(`rate_guard`) это не обходит — он проверяется внутри `publish_queued_post*`
независимо от того, когда сработал цикл.

### Telegram-бот управления (start_bot.bat) — 2026-07-04

`start_bot.bat` запускает `app/control_bot.py` — бот удалённого управления софтом.
**Тот же бот, что публикует посты** (@NewsPost1Bot, `CONTROL_BOT_TOKEN` в `.env` =
тот же токен; по явному запросу пользователя «токен тот же»). Один бот, две роли:
long-polling команд в личке + `sendMessage` постов в канал — не конфликтует, т.к.
polling ведёт только процесс бота. Команды: `/run` `/stop` `/status` `/publish`
`/queue` `/provider <name>`, плюс `/nature_*` и `/shorts_*` (см. ниже, "Единый
пульт управления"). Доступ только у владельца — первый, кто нажал `/start`
в личке (сохраняется в БД `settings.control_bot_owner_id`), либо задать
`CONTROL_BOT_OWNER_ID` в `.env`. Логика команд — чистые функции в `control_bot.py`
(тестируются без aiogram), aiogram-обвязка `build_dispatcher` тонкая.

**`ServiceController` (`app/service_controller.py`)** — общий примитив старт/стоп
сервиса для веб-лаунчера И бота (убрана дублировавшаяся логика потока/asyncio).
Loop и stop_event создаются синхронно в `start()` (не внутри потока) — иначе быстрый
`/stop` сразу после `/run` не находил их и висел весь join-timeout.

### AI-уникализатор — два режима использования (2026-07-04, обновлено)

Ядро — `app/core/media/uniquifier.py`: незаметные глазу трансформации (микро eq
яркость/контраст/насыщенность/гамма, крошечный кроп-и-масштаб обратно) + полная
очистка метаданных + высококачественный энкод (crf 18 / JPEG q95) — **разрешение и
fps исходника СОХРАНЯЮТСЯ**, качество не понижается.

1. **Встроено в прод-пайплайн публикации** (`app/core/video/watermark.py::VideoWatermarker`,
   параметр `uniquify_enabled`) — при `images.uniquify.enabled: true` в config.yaml
   уникализация видео происходит АВТОМАТИЧЕСКИ при подготовке каждого поста с видео,
   в ОДНОМ ffmpeg-проходе вместе с watermark (не два ре-энкода). Трансформация
   детерминированна по `post_id` (`build_post_video_uniquify_filter`) — разные посты
   получают разные, но воспроизводимые (не случайные при каждом запуске) параметры.
   Тот же тумблер, что уже управлял уникализацией фото — единая настройка на оба
   типа медиа. **Это была явная правка пользователя** ("стоп, я хочу этот уникализатор
   сделать не как отдельный функционал, а уже встроенный... скачал видео и текст,
   сделать уникальное видео и рерайт текста и выложил пост") — изначально уникализатор
   был реализован ТОЛЬКО как ручная фича бота, это было ошибкой понимания задачи.

2. **Личный инструмент пользователя в боте** (не прод-пайплайн) — присланное файлом
   видео/фото (до 20 МБ) → 5 уникальных версий назад документами (для перезаливов
   в разные соцсети, не связано с публикацией в @NewsThreeWord/VK). Использует ту же
   библиотеку (`generate_video_variants`/`generate_image_variants`, N вариантов по
   индексу), но отдельный набор функций от продового `build_post_video_uniquify_filter`
   (там 1 вариант по post_id, тут N вариантов по индексу для ручного выбора).

Требует ffmpeg (уже в Dockerfile).

## Соглашения по коду

- Слои: `ui/` → только вызовы `core/*`, без бизнес-логики. `core/*` не знает о Qt. БД — только через `db/repository.py`.
- Каждый `ImageProvider` / `Publisher` — отдельный класс за общим интерфейсом.
- Промпты для LLM — только в `/prompts/*.txt`, не хардкодить в коде.
- Полный код-стайл — по правилам `.claude/rules/ecc/common` и `.claude/rules/ecc/python` (уже подключены в проект).
- **Коммит = деплой, делать без вопроса.** По прямому запросу пользователя (2026-07-05) — тестируешь, зелёные тесты, коммитишь и даёшь `post-commit`-хуку задеплоить, не спрашивая разрешения каждый раз. **Важная оговорка**: `deploy.sh` синкает файлы С ДИСКА (`tar app prompts`), а не по `git`-состоянию — незакоммиченные изменения в `app/`/`prompts/` всё равно уедут на прод при следующем `git commit` любого файла. Если в рабочей копии есть незавершённая/неподтверждённая правка где-то в `app/`, для чистоты либо закончи её тоже, либо унеси из `app/` временно — иначе она задеплоится как побочный эффект.

## Инварианты (нельзя нарушать)

- Никакого поиска новостей по всему интернету — только источники, добавленные пользователем.
- Никакого парсинга случайных изображений из поисковой выдачи — только пост/лицензионные сток-API/локальная генерация.
- ~~Никакой обработки изображений для обхода антидубликат-алгоритмов~~ — **инвариант отменён пользователем 2026-07-02** (явно, через AskUserQuestion, приняв юридический/ToS-риск). Реализована уникализация фото: кроп 1% + гауссов шум + удаление EXIF (`app/core/images/uniquifier.py`, включается через `images.uniquify.enabled` в config.yaml). Метаданные чистятся всегда при сохранении watermark; кроп/шум — только при `enabled: true`.
- **LLM по умолчанию — облачный Groq (`llama-3.1-8b-instant`).** Хронология: 2026-07-03 по запросу пользователя переключали на локальную Ollama (`qwen2.5:3b`), но живой тест вскрыл две проблемы: (1) 3B-модель **галлюцинирует факты** (придумала цитату Путина, ссылку на Bloomberg, неверно объяснила утильсбор), (2) на этой машине (8 ГБ RAM, без дискретной GPU, i3-1215U) Ollama гоняет модель на CPU и выдаёт **>60с на вызов** — один цикл проверки = десятки минут, боевой режим нереален. 2026-07-04 пользователь решил вернуться на Groq до появления сервера с GPU ("когда сервак будет норм — поставлю её"). **Ollama вернётся дефолтом только на машине с GPU; на CPU-only её дефолтом не ставить.** Переключение — одна строка `llm.provider` в `config.yaml`, код всех трёх провайдеров рабочий.
- Никакого обхода лимитов/банов соцсетей.
- **Антиспам-стопор нельзя ослаблять без явного запроса пользователя.** Публикация ограничена жёстким guard (`app/core/publishing/rate_guard.py::check_publish_allowed`), который вызывается ВНУТРИ `publish_queued_post`/`publish_queued_post_vk` — не в обёртке, чтобы никакой вызов (ручной/ошибочный/batch) не мог его обойти. **Текущее значение (2026-07-07, ЯВНЫЙ запрос — «публиковать всё сразу, без лимита»): `max_posts_per_day: 999`, `min_interval_minutes: 0` — дневной лимит и пол интервала сняты.** Сам guard-код остаётся включённым: он по-прежнему блокирует повторную публикацию одного поста в ТУ ЖЕ сеть (баг с 28 повторами в TG 2026-07-05) и разрешает только законный кросс-пост TG→VK — снята только частота/объём. Вернуть лимит = поднять эти два числа в `config.yaml::publishing.schedule`. РИСК: именно частота+объём ранее банили VK — следить. (История: 6/180 → 12/110 «раскачать канал» → 999/0 «без лимита».)

## Известные грабли

- Для Groq (provider по умолчанию) — `GROQ_API_KEY` должен быть в `.env`, иначе явный статус `⛔ LLM недоступна`, не тихий fallback. Для Gemini/Ollama (альтернативные provider) — та же логика, см. ниже.
- Лимит caption в Telegram — 1024 символа, полный текст рерайта может не влезть в подпись к фото.
- VK API публикация фото — двухшаговая (`photos.getWallUploadServer` → `photos.saveWallPhoto`), не один вызов.
- **VK: медиа-загрузка недоступна групповым токеном для ФОТО/ДОКУМЕНТОВ (архитектурное ограничение VK), но для ВИДЕО это был баг в НАШЕМ коде, не ограничение VK** (диагностировано и исправлено 2026-07-04). `photos.getWallUploadServer`/`getUploadServer`, `docs.getUploadServer` групповым токеном — `[27] method is unavailable with group auth`, это **жёсткое архитектурное ограничение VK на уровне метода**, нужен отдельный `VK_PHOTO_UPLOAD_TOKEN` (личный админский). Видео тоже требует этот личный токен (тот же `[27]` на групповом), но при живом тесте с личным токеном `video.save(..., wallpost=False)` падал `[10] Internal server error` — оказалось, `vk_api` сериализует Python `False` в строку `"False"`, которую VK не может разобрать как флаг. Фикс: `wallpost=0` (int), не `False` (`app/core/publishing/vk_publisher.py::_upload_video`). - **`status == "published"` — недостаточно детальный флаг, если публикация идёт в несколько сетей.** Баг (2026-07-05): один пост ушёл в TG `@NewsThreeWord` 28 раз подряд за ~5 часов. Причина — `rate_guard.check_publish_allowed()` разрешал ЛЮБУЮ повторную публикацию поста со `status == "published"` без проверки, в какую именно сеть — это было сделано умышленно, чтобы пропустить законный кросс-пост (TG прошёл → потом VK), но пропускало и повторный выбор в ТУ ЖЕ сеть. Точный механизм повторного выбора уже опубликованного поста не установлен на 100% — вероятная причина: серия частых передеплоев сервиса в тот же день (`AUTOSTART_SERVICE` запускает `cycle_job()` немедленно при каждом рестарте) в сочетании с этим багом гварда. Фикс: `ProcessedPost` получил раздельные поля `published_tg_at`/`published_vk_at` (самолечащаяся миграция), `check_publish_allowed(..., network="tg"|"vk")` блокирует публикацию в сеть, где пост уже выходил, и разрешает без лимита только кросс-пост во ВТОРУЮ сеть. Если добавляешь третью сеть публикации (напр. Instagram) — ей тоже нужно отдельное поле `published_<сеть>_at`, не общий `status`.
- **Успешная публикация раньше не логировалась вообще** — только `rate_guard`-отказы шли в лог как WARNING, историю реальных отправок было видно только через `published_tg_at`/`published_vk_at` в БД. Добавлен явный INFO-лог на каждый реальный `repo.mark_published()` (`app/core/publishing/queue_service.py`, `vk_queue_service.py`) — "Пост N опубликован в TG/VK".
- **`AUTOSTART_SERVICE` + частые передеплои во время активной разработки = частые немедленные циклы публикации на проде.** Каждый рестарт сервиса сразу запускает `cycle_job()`. При активном дебаге лучше группировать коммиты, а не деплоить на каждый маленький шаг прямо на прод — иначе накопление рестартов может маскировать/провоцировать гонки (см. пункт выше про 28 повторов).
- **SimHash даёт беззнаковое 64-битное число, а SQLite INTEGER — знаковый** — `sqlite3` кидает `OverflowError: Python int too large to convert to SQLite INTEGER` на реальных хэшах постов, где старший бит установлен (~50% случаев). Исправлено: `repository.py::_to_signed_64`/`_from_signed_64` конвертируют на границе БД (запись/чтение), вся остальная логика (`app/core/filters/deduplication.py`) продолжает работать с натуральным беззнаковым представлением. Регрессия: `tests/test_repository_posts.py::test_create_raw_post_handles_content_hash_above_signed_64_boundary`. Обнаружено только в реальном прогоне `run_check_cycle` с реальными VK-постами — юнит-тесты с маленькими тестовыми хэшами (42, 100) этот баг не ловили, т.к. не превышали границу 2**63.
