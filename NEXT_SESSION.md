## КРИТИЧНЫЙ баг найден и исправлен — прочитать перед следующими правками rate_guard

**Инцидент**: один и тот же пост (про топливо в Ленобласти) ушёл в TG-канал
`@NewsThreeWord` **28 раз подряд** за ~5 часов (обнаружено пользователем по
скриншотам канала, не нашим мониторингом — см. "Диагностика логами ещё не
покрывает всё" ниже).

**Причина**: `rate_guard.check_publish_allowed()` разрешал ЛЮБУЮ повторную
публикацию поста, если у него `status == "published"` — это было сделано
специально, чтобы пост мог уйти во ВТОРУЮ сеть (TG успешно, потом VK) без
дневного лимита/интервала. Но проверка не смотрела, В КАКУЮ ИМЕННО сеть —
поэтому если пост когда-либо (через любой баг/гонку) снова оказывался
выбранным `pick_next_post_to_publish` для сети, где он УЖЕ выходил, стопор
это пропускал безусловно, без единой проверки.

**Точный механизм повторного выбора уже опубликованного поста НЕ установлен
на 100%** — вероятная причина: серия моих собственных частых передеплоев в
этот же день (~10 рестартов сервиса за несколько часов, каждый через
`AUTOSTART_SERVICE` немедленно запускает `cycle_job()`) в сочетании с этим
багом гварда. Если увидишь повтор снова — сначала смотри, не было ли скопления
рестартов сервиса в это время (`grep 'Пайплайн запущен автоматически'
logs/app.log`).

**Фикс**: `ProcessedPost` получил отдельные поля `published_tg_at`/
`published_vk_at` (самолечащаяся миграция). `check_publish_allowed(...,
network="tg"|"vk")` теперь блокирует публикацию в сеть, где пост уже выходил,
и разрешает без лимита только кросс-пост во ВТОРУЮ сеть. `queue_service.py`/
`vk_queue_service.py` зовут `repo.mark_published(post_id, network, ts)`
вместо общего `update_processed_post_status(..., "published")`. Регрессия:
`tests/test_rate_guard.py::test_blocked_when_already_published_to_same_network*`.

**Не проверено**: сам факт, что фикс останавливает БУДУЩИЕ повторы (логика
проверена юнит-тестами, но не было возможности воспроизвести живой инцидент
для сквозной проверки — дождаться следующего реального цикла публикации и
свериться, что `published_tg_at`/`published_vk_at` заполняются верно).

## Диагностика логами ещё не покрывает всё

Добавленное вчера логирование (сколько постов с источника, причина отказа,
причина "нечего публиковать") НЕ поймало бы этот конкретный инцидент — успешная
публикация не логируется явным INFO-сообщением вообще (только WARNING при
отказе rate_guard). Стоит добавить явный INFO-лог при КАЖДОЙ успешной
публикации (`repo.mark_published` вызывается — залогировать post_id + сеть),
чтобы историю реальных отправок было видно в логах, а не только через
`published_tg_at`/`published_vk_at` в БД.

## Известные грабли, добавленные в этой сессии (не наступать снова)

- **`status == "published"` — недостаточно детальный флаг для rate_guard в
  системе с несколькими сетями публикации.** Если добавляешь третью сеть
  (например, Instagram) — ей тоже нужно отдельное поле `published_<сеть>_at`,
  не общий status.
- **`AUTOSTART_SERVICE` + частые передеплои = частые немедленные циклы
  публикации.** При активной разработке с частыми `git commit` (каждый
  автодеплоится и рестартует сервис) держать это в уме — по возможности
  группировать коммиты, а не коммитить на каждый маленький шаг во время
  активного дебага прямо на проде.
- Один цикл `check_interval` = один вызов `run_check_cycle` + сразу
  `pick_next_post_to_publish` в той же корутине — каждый источник в цикле
  обёрнут в try/except отдельно, не убирать эту защиту.
- Скачивание медиа — всегда после проверки на `known_external_ids`, не до.
- `vk_api` сериализует Python `bool` в `"True"`/`"False"`, не в `"1"`/`"0"` —
  проверять типы параметров первым делом при новых непонятных ошибках VK.
