# Мультиканальность («мультиюзинг») — план эпика

**Цель (запрос пользователя 2026-07-08):** превратить плоский одно-канальный софт в
мультиканальный. 4 независимых канала в одном приложении, каждый со своими источниками,
оформлением, фильтрами, лимитом и целевыми каналами публикации. Это шаг к «супер-софту»
и продукту (позже — мультиюзер/биллинг для чужих).

## Архитектура: плоское → мультиканальное

Сейчас всё глобально в `config.yaml` (`AppConfig`): один поток источников → одна пара
таргетов (TG+VK) → одно оформление/фильтр/лимит. Точки расслоения:
- `Source` (models.py) — нет привязки к каналу → `channel_id`.
- `run_check_cycle` (check_cycle.py) — перебирает все источники в один поток → перебор ПО КАНАЛАМ.
- `_publish_to_all` (headless_service.py) — публикует в глобальные таргеты → таргеты канала.
- Очередь/лимит/rate_guard (`list_fresh_queued_posts`, `count_published_since`,
  `mark_published`) — глобальные → per-channel.
- `AppConfig` — станет ДЕФОЛТАМИ; канал переопределяет своим блоком настроек.

### Модель данных
- Новая таблица `Channel`: имя, enabled, таргеты (tg/vk: token_env + destination,
  vk_upload_token_env), `settings_json` (Text — фильтр/оформление/лимит/стиль, гибко без
  миграций схемы под каждую настройку).
- `Source.channel_id` → FK channels.id.
- `ProcessedPost` — маршрутизация в таргет канала через raw_post→source→channel
  (в срезе очереди, возможно, добавить channel_id для лимита).
- Секреты — только имена env-переменных в БД (инвариант), токены в `.env`.

## Новые технические вызовы (не было в проекте)
- **Веб-фетчер** для сайтов (Партизанск) — новый тип источника, не соцсеть.
- **Кросс-дедуп** между источниками одного канала (SimHash есть, развернуть на канал).
- **Анти-реклама LLM-классификация** для городского канала.
- **Per-channel лимит** — rate_guard считает по каналу, не глобально.
